# План прототипа на Slint

Обновлено 2026-09-20 после сверки плана, отчёта и исходников.

Цель — получить достаточно данных для решения, стоит ли переносить UI с Tauri/Nuxt на Rust + Slint. Полную приёмку продукта не проводим до этого решения. Прототип остаётся отдельным крейтом `prototypes/slint-shell`; основной продукт не переписываем.

**Целевые платформы остаются Linux, Windows и macOS.** Отсутствие среды или существующая заглушка не считаются поддержкой. При этом решение «продолжить пилот» можно принять по Linux; окончательное решение о переходе на всех трёх ОС требует минимальной проверки каждой платформы, а выпуск — полноценной приёмки.

## 2. Как принимаем решение

Работа разделена на три уровня:

1. **Короткий пилот на основном KDE:** репрезентативный UI, release-сравнение с Tauri, реальный цикл выбора и вставки. Результат: остаёмся на Tauri или продолжаем пилот Slint.
2. **Минимальная платформенная проверка:** Hyprland, GNOME fallback, Windows и macOS. Результат: можно ли планировать полный переход с учётом известных ограничений.
3. **Приёмка перед выпуском:** подробная матрица окружений, способов вызова, разрешений, мониторов и упаковки. Выполняется после решения развивать Slint.

Не требуем закрыть всю матрицу ради следующего шага. При сбое исследуем конкретный риск; при устойчивом результате не умножаем одинаковые проверки. Неудача одной архитектуры попапов не доказывает непригодность Slint вообще, но найденный обход должен входить в оценку стоимости и ресурсов.

## 3. Короткий пилот: что делаем сейчас

### A. Один репрезентативный редактор

Первый приоритет: проверить стоимость переноса реального UI. Не строим галерею всех виджетов и не переносим все вкладки.

За основу взять сценарий `KeymapTab` → `KeyEditModal` → `ActionPickerBody`:

- [x] Показать клавиатуру примерно из 80 клавиш с выделением, hover и открытием редактора выбранной клавиши.
- [x] В редакторе сделать категории действий, поиск и несколько типов значения: текст, числовой параметр, выбор из списка, захват сочетания клавиш.
- [x] Добавить валидацию, disabled-состояния, сохранение и отмену. Редактировать черновик; отмена не меняет сохранённое действие. Повторное открытие показывает сохранённое значение.
- [x] Связать UI с Rust-моделью и callbacks. Достаточно состояния в памяти; полноценный конфиг, mapper и YAML не переносим.
- [x] Добавить тестовый набор из 500 записей в список поиска/действий: проверить фильтрацию, прокрутку и обновление одной записи без сброса выделения или позиции.

Критерий: сценарий можно пройти целиком, его поведение и внешний вид приемлемы, понятна структура компонентов и модели. Зафиксировать фактическое время реализации, ручные обходы и оценку оставшегося порта по группам экранов. Не экстраполировать стоимость только из количества строк Vue.

Реализация и автоматизированный проход завершены 2026-09-20; [результат, снимки и ограничения проверки](slint-prototype-report.md#редактор-3a-2026-09-20). Ручная приёмка физических клавиш, clipboard и фокуса остаётся в 3B.

### B. DnD, формы, тема и вёрстка на том же стенде

- [x] Добавить небольшую редактируемую сетку быстрых действий или эмодзи по образцу `QuickActionsTab.vue` / `EmojiTab.vue`: перетаскивание за ручку, видимое место вставки, прокрутка при переносе за край, отмена, обновление порядка в модели. Порядок сохраняется при повторном открытии экрана; запись на диск не обязательна.
- [x] Проверить кириллицу, выделение, копирование/вставку, Tab/Shift+Tab, Enter/Esc. Захват хоткея не должен случайно активировать сохранение или закрытие формы.
- [x] Проверить модалку, возврат фокуса после её закрытия, выпадающий список возле края окна и прокручиваемое содержимое. Достаточно по одному примеру каждого взаимодействия.
- [x] Переключать dark/light без пересоздания окна, с едиными токенами для стандартных и собственных компонентов. Проверить также оба попапа: тема передаётся между процессами, включая скрытые окна.
- [x] Переключать ru/en на лету на пилотном экране и попапах через механизм локализации, пригодный для дальнейшего порта; проверить длинные подписи. Перевод всего продукта не нужен.
- [x] Проверить минимальный рабочий размер окна и масштабы 125%/150%: текст, иконки, обрезание, скролл и области клика.
- [ ] Один раз проверить IME, если доступна настроенная среда; иначе явно оставить непроверенным до платформенной приёмки.

**Статус 3B:** реализация и автоматизированный проход завершены; отметки выше относятся к Slint/Winit в изолированном X11-стенде на 100%/125%/150% и отдельной проверке IPC со Spell в KDE Wayland. [Результаты, снимки, команды и стоимость](slint-prototype-report.md#взаимодействия-3b--2026-09-20). Физический ввод и Wayland clipboard требуют ручной проверки; IME недоступен и остаётся непроверенным до платформенной приёмки.

DnD нужен для перестановки элементов внутри приложения, которая уже есть в продукте. Перетаскивание файлов из проводника пока вне задачи. Возможности проверять на закреплённой версии Slint и выбранном backend, а не только по документации latest.

Критерий: базовые взаимодействия не требуют неприемлемого объёма собственного инфраструктурного кода. Если DnD или формы требуют сложного обхода, записать его стоимость до расширения пилота.

### C. Release-сравнение с Tauri

- [x] Собрать release текущей связки Slint + Spell и текущего Tauri на одной машине.
- [x] Начать с одного подходящего рендерера winit-настроек. Остальные исследовать только при проблемах с качеством, памятью или задержкой; не повторять всю матрицу для трёх рендереров.
- [x] Измерить память всего дерева процессов: старт со скрытыми окнами; после показа обоих попапов и скрытия; открытый пилотный редактор с 500 записями; редактор после скрытия.
- [ ] Измерить первое и повторное открытие обоих попапов, а также повторное открытие настроек. Slint измерен до `t5` сериями 100/100; для Tauri сохранено только время возврата API, не сопоставимая готовность к вводу.
- [x] Перепроверить задержку страницы 1500 эмодзи в release. Оптимизировать её сейчас только если проблема затрагивает реальный сценарий; отдельно принять обычную страницу и список 500 записей.
- [x] Отметить CPU в прогретом простое: скрытые окна не должны постоянно перерисовываться или загружать ядро.

Tauri содержит больше функциональности, чем пилот: сравнение памяти открытых настроек — предварительная оценка, а не доказательство итогового потребления после порта. Использовать близкие данные и сценарии; явно записывать оставшиеся различия.

Исходные цели остаются ориентирами: PSS ≤40 МиБ в простое, ≤80 МиБ с настройками, p95 повторного открытия до готовности к вводу ≤50 мс, первое открытие ≤100 мс. Это не автоматический вердикт: важны выигрыш относительно Tauri и стоимость миграции. Значения &gt;100 МиБ в простое или p95 &gt;150 мс требуют объяснения и решения до продолжения.

Критерий: показать абсолютные значения и разницу с Tauri в МиБ, процентах и миллисекундах. Если выигрыш мал или достигается ценой ухудшения поведения, не расширять переписывание без явной причины. При неопределённых результатах повторить только спорное измерение.

### D. Реальный цикл выбора и вставки на KDE

- [ ] Подключить минимальный путь вставки выбранного текста и эмодзи, используя подходящие части существующего нативного кода. Тестовой A недостаточно; полноценный mapper не переносить.
- [ ] Проверить основной evdev-хоткей: открыть → первая клавиша/поиск → выбрать → закрыть → вернуть фокус → вставить ровно один раз в исходное приложение.
- [ ] Для каждого попапа выполнить по 5 выборов поверх браузера, IDE и терминала: 15 успешных циклов на попап. В набор включить кириллицу, эмодзи и заранее зажатый модификатор с последующим отпусканием.
- [ ] Проверить отмену Esc и потерю фокуса: по одному случаю каждого вида в каждом приложении, без вставки и зависших модификаторов. Если пользователь успел переключить приложение, ввод не должен попадать в постороннее окно.
- [ ] Кнопку настроек, меню трея и IPC проверить по одному успешному открытию каждого попапа. Шорткат DE проверить, если он нужен выбранному пути активации; отдельная серия по 20 вызовов для каждого способа сейчас не нужна.
- [ ] Визуально подтвердить цветные эмодзи, прозрачность, отсутствие обрезания, нужное размещение и отсутствие лишней кнопки панели задач.

Критерий: все попытки доставляют содержимое правильно; любая потеря или ошибочная доставка ввода требует исправления и повторения затронутого сценария. Уже выполненные 20/20 evdev и 500 циклов не повторять без изменений lifecycle/input или новых симптомов.

## 4. Минимальная проверка других платформ

Выполнять после положительного результата короткого пилота, до окончательного решения о полном переходе. Без доступной среды статус остаётся «не проверено», решение — условным.


| Окружение                                     | Минимум для решения                                                                                                                                                        |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hyprland + waybar                             | Spell: трей, оба попапа, нижнее размещение, основной хоткей, первая клавиша и реальный возврат ввода                                                                       |
| GNOME Wayland + нужный tray backend/extension | Fallback на обычное окно winit без декораций по центру: проверить фактическую активацию, хоткей и возврат ввода; наличие маршрута fallback в коде не считается результатом |
| Windows                                       | Release-сборка, запуск редактора, трей, оба попапа, нативный хоткей и возврат ввода                                                                                        |
| macOS                                         | То же, плюс необходимые разрешения и рабочий путь после их выдачи                                                                                                          |


Для каждого окружения достаточно по 5 полных циклов на попап поверх одного реального приложения и одной отмены. Это поиск архитектурных препятствий, не статистическое доказательство надёжности. На Windows/macOS дополнительно проверить открытие формы, текст/clipboard и тему, нижнее размещение с учётом панели/Dock.

Перед сборками Windows/macOS:

- [ ] Ограничить Linux-зависимости и модули Cargo target dependencies и `#[cfg(target_os = "linux")]`. Feature `spell` не заменяет платформенную изоляцию.
- [ ] Добавить минимальные адаптеры трея, хоткея, IPC, активного окна, возврата ввода и метрик. Linux evdev/uinput, Wayland, ksni и `/proc` не должны попадать в обязательный путь других ОС.
- [ ] Сохранить общий Slint UI; нативные отличия держать в адаптерах. Полноценный mapper, определение раскладки и системные действия оценить отдельно: выбор UI не реализует их автоматически.

Linux X11 и расширенную матрицу мониторов оставить до приёмки перед выпуском. Если обнаружится платформенный блокер, проверить конкретную альтернативу и её стоимость; не начинать полный порт в предположении, что проблема решится позже.

## 5. Стоимость поддержки выбранной архитектуры

Выбираем фактически **Slint + winit-настройки + отдельный Spell-процесс + локальные исправления Spell**. Эта стоимость входит в решение наряду с памятью и скоростью.

- [ ] Перечислить собственные изменения Spell, их тесты и зависимость от внутренних API Slint; зафиксировать закреплённые версии и путь дальнейшего сопровождения: upstream или локальная копия.
- [ ] Оценить трудоёмкость обновления связки и ограничения выбранных рендереров. Не обновлять зависимости только ради завершения пилота.
- [ ] Проверить понятное поведение при завершении дочернего процесса: основной процесс не зависает; видна ошибка или возможно повторное открытие. Полный механизм автоматического восстановления можно оставить для реализации продукта.
- [ ] По результатам редактора оценить стоимость остальных экранов, модели состояния, локализации и недостающих нативных адаптеров. Отдельно перечислить возможности Tauri, которые придётся заменить.

Критерий: есть объяснимая оценка миграции и сопровождения, а не только успешный показ попапа.

## 6. Минимальная методика измерений

### Память и условия

- Release, одна машина/сессия, одинаковый масштаб и данные, без параллельной сборки. Записать версии, backend, renderer и параметры запуска.
- Linux: PSS из `/proc/<pid>/smaps_rollup`, дополнительно RSS, сумма родителя и всех потомков. Использовать существующий `scripts/mem.sh`; для Tauri учитывать WebKit-процессы.
- Основная точка простоя — после прогрева и скрытия всех окон. Стартовую точку записывать отдельно: скрытое создание UI-компонента не означает прогретое нативное окно.
- Сделать три независимых запуска и показать разброс памяти. Не смешивать результаты debug и release.
- GPU allocation может не входить в PSS; отметить ограничение. Подробный учёт GPU нужен сейчас только если без него вывод о выигрыше неоднозначен.
- Windows: private bytes/working set; macOS: physical footprint/resident memory, с указанием инструмента. Сравнивать с Tauri на той же ОС, не выдавать эти величины за Linux PSS. Полный performance benchmark других ОС для минимальной функциональной проверки не обязателен.

### Задержки

Сохранить существующие CSV и точки измерений:


| Метка             | Значение                                                                  |
| ----------------- | ------------------------------------------------------------------------- |
| `t0_trigger`      | Получен хоткей/IPC/нажатие кнопки                                         |
| `t1_on_ui_thread` | Начат UI callback                                                         |
| `t2_shown`        | Возврат из show или отправка запроса показа; не готовый кадр              |
| `t3_first_frame`  | Завершение отрисовки; у текущего Spell — render + commit, не presentation |
| `t4_focused`      | Backend сообщил получение фокуса                                          |
| `t5_first_key`    | Попап реально обработал первую клавишу                                    |


- Для выбранной конфигурации: 100 повторных открытий каждого попапа, p50/p95/max по t4 и t5 относительно t0; отдельно число успешных попыток и пропуски. Провалы не исключать из вывода о надёжности.
- Первое открытие измерить при трёх независимых запусках и показать все значения; не называть p95 по трём попыткам. Отличать первое открытие от холодного старта ОС/дискового кеша.
- Раскрывать ожидания тестового стенда: если клавиша отправляется только после фокуса или с задержкой, t5 включает это ожидание. Не выдавать его за чистую задержку рендеринга.
- Межпроцессный путь входит в задержку. Текущая передача времени через SystemTime чувствительна к изменению часов; записать ограничение и не менять часы во время серии.
- Для Tauri использовать аналогичные точки готовности. Видеозапись 60 fps допустима для грубой оценки появления, но не доказывает готовность к вводу и не позволяет уверенно сравнивать разницу в несколько миллисекунд.
- Недоступные метрики явно помечать; не подменять t3/t4 возвратом из show.

Повторные 500 циклов нужны при изменении lifecycle или подозрении на утечку. Уже имеющаяся серия не показывает существенного роста памяти, но не доказывает отсутствие утечек во всех сценариях.

## 7. Что отложено до реализации и приёмки перед выпуском

Эти пункты не блокируют короткий пилот, но остаются обязательными для заявленной поддержки продукта:

Для Spell: Emoji 520×460, Quick 520×500 логических px, снизу по центру, отступ 24 от доступной рабочей области, overlay, exclusive zone 0; не менять геометрию других окон. Для Windows/macOS — такое же нижнее размещение; для GNOME fallback — центр.

## 8. Критерии решения и отчёт

Обновлять [существующий отчёт](slint-prototype-report.md), сохраняя исторические результаты и добавляя актуальный вывод в начало. Старые незакрытые этапы не превращать в выполненные из-за сокращения матрицы: указывать, что отложено и почему.

В отчёте достаточно:

1. Результат редактора и DnD: короткая запись/скриншоты, что работает, фактическое время реализации, обходы и оценка порта.
2. Release-таблица Slint/Tauri: память по четырём точкам, первое и повторное открытие, разброс и условия.
3. Результаты реального ввода: окружение, попап, успешные/все попытки, отмены и обнаруженные сбои.
4. Платформенная таблица: проверено / не проверено / блокер. Отдельно сборка и реальное поведение.
5. Цена сопровождения Spell/IPC и итоговое решение.

Возможные решения:


| Решение                  | Основание                                                                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Остаёмся на Tauri        | Выигрыш не оправдывает перенос; UI/ввод имеют блокеры или сопровождение слишком дорого                                                           |
| Продолжаем пилот Slint   | KDE-редактор, release-сравнение и ввод убедительны; другие платформы ещё не закрыты. Это не разрешение считать весь продукт переносимым          |
| Планируем полный переход | Пройдены короткий пилот и минимальные проверки обязательных платформ, известны стоимость и ограничения; полная приёмка остаётся условием выпуска |


## 9. Ближайший порядок работ

1. Редактор 3A и автоматизированная часть 3B готовы. Завершить короткий ручной проход 3B в KDE (физический ввод и clipboard); не расширять KDE-матрицу заранее.
2. Провести release-сравнение из 3C и реальную вставку из 3D; оценить сопровождение по разделу 5.
3. Обновить отчёт и решить, оправдано ли продолжение пилота. Если нет — остановить перенос.
4. При положительном результате закрыть минимальные платформенные проверки из раздела 4 и оценить полный переход.
5. После решения о переходе включить раздел 7 в план реализации и выпуска.

Оценку оставшегося времени дать после первого редактора. Прежняя оценка «6–7 дней» не отражает уже сделанную работу, новые UI-проверки и платформенные адаптеры.
