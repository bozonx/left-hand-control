# План прототипа на Slint

Цель — за минимальное время проверить всё, что определяет решение «переводить ли UI с Tauri/Nuxt на Rust + Slint». Приложение **не портируем**: только каркас процесса, трей, окна-попапы и одно «окно настроек» с типовыми виджетами. Всё остальное — заглушки.

**Обязательные целевые платформы — Linux, Windows и macOS.** Итоговое приложение должно обеспечивать полный рабочий цикл на всех трёх ОС: трей, настройки, попапы, хоткеи, перехват/переназначение клавиш, определение раскладки, системные действия и ввод в исходное приложение. В прототипе проверяем оболочку и минимальный нативный путь вызова/возврата ввода; полноценный mapper остаётся отдельной задачей миграции. Существующие заглушки Windows/macOS не считаются поддержкой.

По итогам прототипа должен получиться короткий отчёт с цифрами (раздел 8) и решение: идём дальше / идём, но с layer-shell для попапов / не идём.

## 2. Что НЕ делаем

- Не портируем mapper, конфиг, редакторы, YAML-раскладки.
- Не трогаем текущее приложение (кроме опциональных замеров baseline, см. раздел 6).
- Не делаем полноценный дизайн — достаточно, чтобы окна выглядели «как настоящие» по сложности отрисовки.
- Не переносим полный mapper в прототип; для Windows/macOS обязательно реализуем и проверяем минимальные нативные адаптеры оболочки, хоткея, фокуса и тестового ввода.

## 3. Структура прототипа

Отдельный cargo-крейт вне основного приложения, не входит в workspace и в сборку Tauri:

```
prototypes/slint-shell/
├── Cargo.toml
├── build.rs                 # slint-build: компиляция .slint
├── ui/
│   ├── popup-emoji.slint    # сетка эмодзи, страницы, навигация стрелками
│   ├── popup-quick.slint    # список быстрых действий, навигация, Enter/Esc
│   ├── settings.slint       # «окно настроек» с типовыми виджетами
│   └── theme.slint          # цвета/токены, dark/light
├── src/
│   ├── main.rs              # event loop, создание окон, связка потоков
│   ├── tray.rs              # ksni
│   ├── hotkey.rs            # evdev-листенер (фоновый поток)
│   ├── ipc.rs               # unix socket: `slint-shell show emoji|quick`
│   ├── focus.rs             # детект активного окна (копия минимума из src-tauri/src/active_window)
│   ├── inject.rs            # uinput: эмуляция нажатия после скрытия попапа
│   ├── position.rs          # центр / курсор (X11, hyprctl, KWin)
│   └── metrics.rs           # тайминги → CSV, RSS/PSS → лог
└── scripts/
    ├── mem.sh               # замер PSS/RSS процесса (и дерева процессов для baseline)
    └── bench-open.sh        # N циклов открыть/закрыть попап, сбор CSV
```

Зависимости (ориентировочно): `slint` (актуальная 1.x, фичи для всех трёх рендереров), `slint-build`, `ksni` (blocking API), `evdev`, `zbus` (KWin/портал), `log` + `env_logger`, `serde`/`serde_json` для конфига-заглушки.

Для проверки layer-shell добавить отдельный вариант попапов на [Spell (`spell-framework`)](https://github.com/VimYoung/Spell), сохранив UI на Slint. Зафиксировать совместимые версии Slint/Spell и доступные рендереры. Проверить совместную работу с окном настроек на winit: один backend Slint выбирается при старте, поэтому возможность совмещения в одном процессе не предполагаем заранее. Если нужен отдельный процесс попапов с IPC, учесть его в замерах памяти и задержек.

**Границы платформенных backend:**

- Общие Slint-компоненты и логика UI используются на Linux, Windows и macOS.
- Spell — только Linux Wayland с layer-shell. Его зависимости и модули ограничить Cargo target dependencies и `#[cfg(target_os = "linux")]`; feature `spell` сама по себе не заменяет платформенную изоляцию.
- На Windows/macOS — Slint/winit и нативные адаптеры окон: те же размеры попапов, нижнее центрирование с отступом от рабочей области выбранного монитора, прозрачность, отсутствие декораций, показ поверх окон, получение и возврат фокуса. Поведение поверх fullscreen проверять отдельно на каждой ОС.
- `evdev`, `uinput`, Wayland, `ksni`, `/proc` и Linux IPC/окружение не должны попадать в обязательный путь других ОС. Для трея, хоткеев, IPC, активного окна, тестового ввода и метрик предусмотреть платформенные реализации. Структура и команды выше описывают Linux-вариант.
- Успешная сборка не заменяет проверку поведения на целевой ОС. Отсутствие Windows/macOS-среды означает незакрытую проверку, а не снятие требования.

## 4. Этапы

Отметки этапов 0–3 относятся к уже проверенному Linux/winit-варианту. Приёмка Windows/macOS ведётся отдельно в этапе 3б.


### ✅ Этап 0. Каркас (0.5 дня)

- Один процесс, один event loop Slint.
- Окна создаются **при старте** и держатся скрытыми: `SettingsWindow`, `EmojiPopup`, `QuickPopup`.
- Фоновые потоки (hotkey, ipc) общаются с UI только через `slint::invoke_from_event_loop` — ровно так же будет работать mapper.
- Выбор рендерера через `SLINT_BACKEND` (`winit-software`, `winit-femtovg`, `winit-skia`), чтобы все замеры делать для каждого.
- Логирование времени с момента `main()` до готовности каждого окна.

Проверяет: Q10 (старт), основу для Q1.

### ✅ Этап 1. Трей (0.5 дня)

- `ksni`: иконка, меню «Настройки», «Эмодзи», «Быстрые действия», «Выход».
- Клик по иконке — показать/скрыть окно настроек.
- Иконка меняется по команде (имитация «mapper включён/выключен»).
- Проверить, что приложение продолжает жить, когда все окна скрыты (у Slint по умолчанию `run_event_loop` выходит при закрытии последнего окна — нужен `run_event_loop_until_quit`).

Проверяет: Q7.

### ✅ Этап 2. Попапы (1–1.5 дня)

**Emoji-попап:**

- Сетка ~8×6 на странице, 5 страниц (≈240 эмодзи), реальный шрифт Noto Color Emoji.
- Навигация стрелками, Enter — выбор, Esc — закрыть, цифры 1–5 — страница.
- Отдельно тестовая страница «тяжёлая»: ~1500 эмодзи в прокручиваемом списке — для замера времени отрисовки.

**Quick-попап:**

- Список ~30 пунктов с иконкой, текстом и подсказкой хоткея, навигация, фильтр по вводу.

**Общее для обоих:**

- Без рамки, прозрачный фон, скруглённые углы, тень (если возможно).
- `always on top` и «без значка в панели задач» — зафиксировать, что реально работает на каждом DE (на Wayland это решает композитор; на KDE допустимо через правило окна — записать, какое).
- Скрытие по Esc и по потере фокуса.

Проверяет: Q6, Q8.

### ✅ Этап 3. Способы вызова и фокус (1 день) — самый важный этап

Три пути вызова попапа, для каждого замеряем тайминги и фокус:

1. **Кнопка в окне настроек.** Окно уже в фокусе, у него есть право получить xdg-activation токен. Это «лучший случай».
2. **Хоткей через evdev в фоновом потоке.** Реальный сценарий — так вызывает текущий mapper. Токена нет. Нужны права на `/dev/input` (группа `input`, как у основного приложения). Хоткей выбрать редкий (например F13 или `ScrollLock`).
3. **Команда через unix socket** (`slint-shell show emoji`), повешенная на глобальный шорткат DE. KDE при запуске команды по шорткату выставляет `XDG_ACTIVATION_TOKEN` в окружении — передаём его по сокету и применяем при показе окна. Проверяем, решает ли это проблему фокуса без layer-shell (запасной вариант архитектуры).

Для каждого пути, 20 вызовов подряд, поверх разных окон (терминал, браузер, IDE):

- Получил ли попап фокус клавиатуры (событие `Focused(true)` через `slint::winit_0xx::WinitWindowAccessor`, плюс проверка, что первая нажатая стрелка сработала).
- Оказался ли попап поверх целевого окна.
- Не «мигает» ли вместо этого значок в панели задач (focus stealing prevention в KDE).

Проверяет: Q2, Q3.

### 🚧 Этап 3а. Slint + Spell: layer-shell на Wayland и fallback GNOME

Статус 2026-09-20: исправлены lifecycle, фокус, автоповтор, модификаторы и
масштабирование локальной копии Spell. В KDE получена серия evdev 20/20 для каждого
попапа; в приватном KWin прошли 500 циклов (плюс два прогрева), расширенная проверка
ввода и 16 проверок геометрии, включая HiDPI, панель и fullscreen. Пользователь
также подтвердил нижнее размещение вручную. Этап **не закрыт**: остаются Hyprland,
GNOME fallback и полная матрица реальных приложений/способов вызова. На тяжёлой
странице 1500 эмодзи обнаружена задержка около 2,6 с в debug.
[Результаты и границы проверки](slint-prototype-report.md#результаты-доработки-3а-2026-09-20).

Обязательная проверка независимо от результата обычных окон на этапе 3. Отметки выполнения этапов 0–3 относятся к варианту winit, а не к Spell.

**Размещение и выбор backend:**

- На KDE Wayland и Hyprland проверить оба попапа через Spell/layer-shell: Emoji — **520×460**, Quick — **520×500** логических пикселей, по центру нижнего края выбранного монитора с отступом **24** логических пикселя. Размеры и отступ задаются явно.
- Использовать слой `overlay`, привязку к нижнему краю и отсутствие резервирования рабочей области (`exclusive_zone = 0`). Отступ 24 отсчитывать от доступного нижнего края с учётом зарезервированного места панели/дока; записать фактическую геометрию. Проверить отсутствие изменения размеров других окон и положение поверх обычных, развёрнутых и полноэкранных приложений.
- Проверить два монитора, выбор целевого монитора, его отключение и масштабы 100%, 125%, 150%: попап не обрезается, размер и отступ сохраняются в логических единицах.
- Проверять наличие протокола layer-shell при запуске. Для **GNOME Wayland — fallback на обычное окно Slint/winit без декораций, целевое положение — центр экрана**, с теми же размерами и функциональностью. GNOME не поддерживает layer-shell; абсолютную позицию обычного окна на Wayland приложение не задаёт. Проверить реальное центрирование Mutter при первом и повторном показе; если нужна настройка или расширение, записать точную зависимость. Отсутствие центрирования считать невыполненным требованием fallback, а не успешным результатом.

**Хоткеи, ввод и жизненный цикл — для обоих попапов и GNOME fallback:**

- Повторить вызов кнопкой, через evdev и IPC/шорткат DE из этапа 3, а также из трея. Основной сценарий для Spell — evdev без activation-токена, 20/20 успешных вызовов поверх терминала, браузера и IDE.
- Настроить и проверить режим `keyboard_interactivity` для layer-shell: фокус сразу после показа, первая клавиша не теряется. Для fallback отдельно проверить активацию обычного окна; наличие fallback само по себе не решает проблему фокуса.
- Проверить стрелки, Enter, Esc, переключение страниц цифрами, хоткеи быстрых действий, поиск с кириллицей, удержание клавиш и повторный хоткей открытия. Нет двойного выполнения, залипших модификаторов и утечки навигационных клавиш в исходное приложение.
- Проверить скрытие по Esc и потере фокуса, повторное открытие, переключение между Emoji и Quick, отсутствие значка в панели задач, прозрачность, скругления, цветные эмодзи и тяжёлую страницу из этапа 2.
- Повторить этап 5: выбор → скрытие → возврат фокуса → тестовый ввод в исходное приложение, 20/20. После отмены ввод не инжектируется, после скрытия layer-shell больше не удерживает клавиатуру. Mapper и действия остаются заглушками в рамках прототипа.
- Повторить замеры задержек, памяти и 500 циклов открытия/закрытия. Для Spell фиксировать фокус по событиям клавиатуры Wayland, доставленным в Slint, и подтверждать первой обработанной клавишей; не полагаться на winit accessor. Проверить работу трея и настроек при скрытых попапах.

Проверяет: Q2–Q6, Q8, Q11 и совместимость backend'ов. Оценку сроков этого этапа уточнить после минимального запуска Spell.

### Этап 4. Позиционирование (0.5 дня)

Нижняя привязка Spell и центрированный fallback GNOME проверяются в этапе 3а; ниже — дополнительные режимы обычных окон.

- Режим «по центру»: на X11 — явные координаты; на Wayland — что делает композитор (зафиксировать для KDE и Hyprland, какие правила окна нужны).
- Режим «у курсора»:
  - X11 — `XQueryPointer`, явная позиция.
  - Hyprland — `hyprctl cursorpos` + `windowrule` / `hyprctl dispatch movewindowpixel`.
  - KDE Wayland — позиция курсора через KWin (скрипт или DBus); выяснить, можно ли потом **переместить** обычное окно в эту точку без layer-shell (ожидание: нельзя без KWin-скрипта/правила).
- Для каждого DE записать: «центр работает / не работает / работает только с правилом», «курсор работает / не работает / нужен layer-shell».

Проверяет: Q4.

### Этап 5. Возврат фокуса и инжект (0.5 дня)

- Перед показом запоминаем активное окно (минимальная копия `src-tauri/src/active_window`).
- По Enter: скрыть попап → ждать, пока активным станет исходное окно (замерить, сколько мс это занимает) → через uinput на Linux или нативный адаптер ввода Windows/macOS нажать клавишу (например, набрать `a`), чтобы убедиться, что ввод попал в нужное окно.
- Сравнить с текущей схемой (`wait_for_post_menu_focus`: опрос каждые 60 мс до 250 мс).

Проверяет: Q5.

### Этап 6. «Окно настроек» (1–1.5 дня)

Не функциональность, а типовые по сложности элементы, чтобы оценить трудоёмкость порта и память «тяжёлого» окна:

- Боковая навигация + 4 таба.
- Список из 500 элементов с редактированием строки (аналог списка правил/макросов).
- Модальное окно выбора действия (аналог `ActionPickerModal`) с поиском.
- Визуализация клавиатуры из ~80 клавиш-кнопок (аналог `KeymapTab`) с выделением и hover.
- Текстовые поля: ввод кириллицы, выделение, копирование/вставка, IME (хотя бы проверить, что не ломается).
- Переключение темы dark/light и языка ru/en на лету (`@tr()` + gettext).
- Проверка на дробном масштабе (125%, 150%) — чёткость текста и иконок.
- Скрытие в трей и **повторное открытие** — время появления. Отдельно вариант «уничтожать окно при закрытии и создавать заново» — сколько памяти освобождается и сколько стоит пересоздание.

Проверяет: Q9, часть Q1.

### Этап 7. Замеры (0.5–1 день)

См. разделы 5–6.

**Исходная оценка Linux-части: ~6–7 рабочих дней плюс этап 3а. Windows/macOS (этап 3б) требуют отдельной оценки.** Если обычные окна не получают фокус на KDE Wayland, проверить Slint + Spell/layer-shell до решения о смене UI попапов. Решение принимаем по результатам Spell на KDE/Hyprland, отдельной проверки fallback на GNOME и обязательной приёмки Windows/macOS; неудача winit сама по себе не исключает Slint для попапов.

## 5. Методика замеров

### Время

В `metrics.rs` фиксируем метки через `Instant` и пишем в CSV:


| Метка             | Где ставится                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| `t0_trigger`      | в потоке evdev/ipc/обработчике кнопки — момент получения хоткея                                                     |
| `t1_on_ui_thread` | начало колбэка в `invoke_from_event_loop`                                                                           |
| `t2_shown`        | после `window.show()`                                                                                               |
| `t3_first_frame`  | первый `RenderingState::AfterRendering` из `set_rendering_notifier` после show                                      |
| `t4_focused`      | `WindowEvent::Focused(true)` через winit accessor                                                                   |
| `t5_first_key`    | первое нажатие клавиши, обработанное попапом (при автотесте — нажатие, эмулированное через uinput сразу после `t0`) |


Главная метрика — `**t4 − t0` и `t5 − t0`** («попап готов к вводу»). Собираем 100 открытий подряд (`bench-open.sh`), считаем p50/p95/max. Отдельно — первое открытие после старта процесса.

Результаты разделять по backend: winit, Spell/layer-shell, GNOME fallback. Для Spell использовать эквивалентные точки показа, завершения первого кадра и получения фокуса в его backend; отсутствие winit accessor/rendering notifier не подменять временем возврата из `show()`. Недоступные метрики явно отмечать. Проверять фактически поддерживаемые Spell рендереры, не предполагая поддержку всех вариантов `SLINT_BACKEND=winit-*`.

### Память

Методика `/proc`/PSS ниже относится к Linux. На Windows фиксировать private bytes и working set, на macOS — physical footprint и resident memory, с указанием инструмента и учётом дочерних процессов. Сравнивать с Tauri на той же ОС; не выдавать разные метрики за эквивалент PSS.

- Основная метрика — **PSS** из `/proc/<pid>/smaps_rollup` (честнее RSS для разделяемых библиотек), дополнительно RSS.
- Для GPU-рендереров (femtovg, skia) часть памяти сидит в драйвере и не всегда видна в PSS — дополнительно посмотреть `/sys/kernel/debug/dri/*/clients` или `radeontop`/`nvidia-smi` в зависимости от видеокарты; отметить в отчёте.
- Точки замера:
  1. сразу после старта (все окна скрыты, трей активен);
  2. после первого показа каждого попапа и скрытия;
  3. с открытым окном настроек (на табе с 500 элементами);
  4. после закрытия окна настроек (скрыто / уничтожено);
  5. после 500 циклов открыть/закрыть попап (проверка утечек, Q11).
- Каждую точку — для трёх рендереров winit и отдельно для доступных рендереров Spell; при нескольких процессах учитывать их суммарный PSS.

Скрипт `mem.sh`: принимает PID, суммирует PSS по процессу **и всем его потомкам** — это же нужно для baseline Tauri (WebKitWebProcess, WebKitNetworkProcess).

### Прочее

- Холодный старт: от `exec` до готовности трея и скрытых окон.
- Размер release-бинарника (с `lto`, `opt-level = "s"`, `strip` — как в текущем `src-tauri/Cargo.toml`).
- Время полной и инкрементальной сборки.
- Системные зависимости: `ldd` на бинарник (ожидаем fontconfig, freetype, libxkbcommon, wayland-client, libGL/EGL; GTK/WebKit — не должно быть).
