# Дизайн аккордового ввода

Статус: предложение к реализации. Документ описывает целевое поведение; перечисленные новые возможности ещё не реализованы.

## 1. Цель и принятые решения

Позволить пользователю построить буквенную, цифровую или командную аккордовую раскладку: например, `D+F → 1`, `D+F+G → Я`, сочетание → макрос, сочетание → временный слой.

Тип распознавания выбирается **в каждом правиле**: «Обычный триггер | Аккорд». Общий режим для всей раскладки не требуется. Обычный триггер может быть как одиночной клавишей, так и сочетанием, например `Shift+Slash`.

Принятые ограничения интерфейса:

- Двойное нажатие недоступно для многоклавишных триггеров обоих типов. Существующие значения игнорируются движком, как в текущей реализации.
- Слои и действие при долгом удержании доступны для аккордов.
- «Удерживать другую клавишу / сочетание» сохраняется при активации слоя, вместе с настройками `isolate` и `holdFor`.
- Старые правила без нового поля продолжают работать по прежней логике.

В первой версии поддерживается набор отдельных аккордов с полным отпусканием использованных клавиш перед их повторным использованием. Непрерывный набор с общей зажатой клавишей между соседними аккордами — отдельный последующий этап, а не неявное обещание первой версии.

## 2. Ограничения текущего движка

Распознавание находится в `crates/lhc-core/src/mapper/engine/mod.rs`, метод `handle_chord()`. Триггеры разбираются через `profile::key_catalog::trigger_keys()`; правила собираются в `engine/builder.rs`.

Текущая логика распознаёт сочетание, когда все его клавиши физически нажаты, но не буферизует начало возможного аккорда. Короткое сочетание захватывает свои клавиши сразу; расширить его после этого нельзя. Отпускание любой клавиши завершает сочетание, а оставшиеся участники не могут повторно участвовать до своего отпускания. Правила сочетаний общие; таблицы назначений слоёв разрешают одиночные клавиши.

Проверка последовательностей непосредственно через движок выявила:

| Конфигурация и ввод | Текущее поведение |
| --- | --- |
| `D+F → text:1`; нажать D, затем F | До результата аккорда выдаётся `KEY_D down`. В приложении может появиться лишняя D; последующий key-up её не отменяет |
| `D+F → 2`, `D+F+G → 3`; нажать D, F, G | Захватывается `D+F`; третий участник не расширяет аккорд |
| `D+F`, затем `F+G`, не отпуская F | F остаётся использованной первым сочетанием; второй аккорд не распознаётся |
| `D+F → слой + удерживать Alt` | Alt зажимается после распознавания и отпускается при завершении сочетания; начало D при этом ещё не защищено от выдачи |

Одиночные назначения участников могут изменить конкретную выдачу, но не заменяют общий алгоритм распознавания.

## 3. Модель конфигурации

Предлагаемые новые поля; имена окончательно согласовать при реализации:

| Поле | Место | Семантика |
| --- | --- | --- |
| `triggerMode: "normal" \| "chord"` | Правило | Отсутствие означает `normal` |
| `defaultChordWindowMs` | Настройки | Максимальное время сборки от первого нового участника |
| `conditionLayerId` | Правило, последующий этап | Область действия правила: отсутствие — глобальное, значение — конкретный активный слой |

Предварительное значение окна сборки — 50 мс. Это стартовый параметр для испытаний, а не подтверждённое измерениями оптимальное значение. Предлагаемый допустимый диапазон — 10–250 мс. Не добавлять индивидуальные таймауты правил в первой версии: пересекающиеся сочетания должны иметь одно окно выбора.

`layerId` сохраняет существующий смысл: слой, который правило **активирует**. Его нельзя использовать одновременно как область, **в которой** правило действует.

Пример целевой записи правила:

```json
{
  "key": "KeyD+KeyF",
  "triggerMode": "chord",
  "tapAction": "text:1",
  "holdBehavior": "none"
}
```

Новые поля провести через профильную модель, runtime-конфиг, редактируемый `ConfigDocument`, JSON, импорт/экспорт YAML, TypeScript и обе оболочки. Не ограничиваться добавлением поля в `mapper::config::Rule`. Для YAML предложить отдельное поле `triggerMode`; отсутствие сохраняет старый формат и поведение.

## 4. Что означает выбор «Аккорд»

Настройка принадлежит правилу, но буферизация неизбежно затрагивает его физические клавиши. Если D одновременно самостоятельная буква и часть `D+F`, невозможно сразу выдать D и затем гарантированно убрать её при появлении F.

Задерживаются только новые нажатия клавиш, которые могут начать доступный аккорд. Остальные клавиши сохраняют обычный путь обработки, кроме необходимости соблюсти порядок относительно уже накопленного ввода.

При отключении всех подходящих аккордовых правил новые события идут по прежнему пути без окна сборки. Правила с неподходящими условиями не должны создавать задержку.

Пересекающиеся наборы клавиш движок индексирует автоматически. Пользователь не создаёт группы вручную. Группа нужна для поиска кандидатов и диагностики; транзитивная связь правил не означает, что все клавиши группы образуют один гигантский аккорд.

## 5. Сборка и выбор аккорда

### Начало

Новое нажатие потенциального участника открывает сессию распознавания. Движок сохраняет событие, исходное время и снимок доступных кандидатов. Конец окна равен времени первого участника плюс `defaultChordWindowMs`; новые участники не продлевают его.

Участники аккорда должны быть физически нажаты одновременно хотя бы в момент завершения сборки. Последовательность D-down, D-up, F-down не является `D+F`. Порядок нажатия участников значения не имеет.

Клавиша, уже выданная обычным путём до начала сессии, не может быть задним числом поглощена аккордом. После истечения окна несостоявшееся начало становится обычным вводом; позднее дополнение не превращает его в аккорд.

### Завершение выбора

Аккорд выбирается при одном из событий:

1. Собран полный кандидат, у которого нет доступного строгого расширения: можно выбрать немедленно.
2. Истекло окно сборки: выбрать самый длинный полностью собранный кандидат.
3. Отпускается участник: выбрать самый длинный кандидат, полный непосредственно перед этим отпусканием; затем обработать отпускание уже выбранного аккорда.
4. Приходит новое событие, которое не может продолжить сессию: сначала завершить выбор или вернуть накопленный ввод, затем обработать новое событие.

Отпускание посторонней клавиши, нажатие которой уже было выдано до сессии, проходит через учёт удержаний и не должно произвольно завершать сборку. Клики мыши и новые посторонние нажатия служат границей: ожидающий ввод должен разрешиться до них, чтобы комбинации с модификаторами имели правильный порядок.

При `D+F` и `D+F+G` собранное `D+F` ждёт G, отпускания или конца окна. Действие короткого сочетания не выдаётся заранее и не отменяется задним числом.

Выбор делается по самому длинному полному набору. Два разных максимальных кандидата одинаковой длины считаются неоднозначностью: не выбирать случайно по порядку `HashMap` или файла. Для первой версии при такой неоднозначности вернуть обычный ввод и показать диагностируемый конфликт. Статическая валидация должна заранее выявлять очевидные случаи.

События, не принадлежащие выбранному набору, не поглощаются молча: возвращаются в обычную обработку с соблюдением порядка. Для первой версии не выполнять несколько действий из одного набранного набора и не искать оптимальное разбиение на несколько аккордов.

### Возврат одиночного ввода

Если полного кандидата нет, накопленные события передаются в существующую обработку одиночных правил и назначений. Это не просто raw passthrough: должны работать remap, native, swallow и одиночные tap/hold/double-tap.

Повторная обработка обходит распознаватель аккордов, чтобы не возникало повторной буферизации. Сохраняются порядок и исходные времена событий. Истёкшие tap/hold-дедлайны разрешаются явно до следующих событий; нельзя позволить позднему replay ошибочно превратить короткое нажатие в удержание или пропустить состоявшееся удержание.

Повторные key-down от автоповтора не добавляют участников и не открывают новую сессию. После возврата обычного ввода удержание и повтор работают через существующий backend; накопленные повторы не выдаются залпом.

## 6. Жизненный цикл выбранного аккорда

У выбранного аккорда есть собственный идентификатор экземпляра и набор участников. Не использовать первую клавишу набора как единственную идентичность: она может быть частью нескольких правил и одиночного назначения.

Точка начала удержания — время нажатия последнего участника выбранного набора. Пока выбор не завершён, внешние эффекты не выполняются. После выбора движок учитывает уже прошедшее время; окно сборки не прибавляется скрытно к порогу удержания.

- Короткое действие выполняется один раз при первом отпускании участника, если удержание не выбрало другую ветку.
- Без настроенного удержания обычное действие аккорда не должно теряться из-за долгого нажатия. В режиме `chord` отсутствие hold-функции не означает выдачу исходного физического сочетания после таймаута.
- Слой действует, пока удерживаются все участники. Сохраняется текущая семантика tap/hold: при подавленном tap слой включается после выбора сразу; при отдельном tap — после решения об удержании.
- Долгое действие выполняется один раз после заданного срока непрерывного удержания всех участников. Раннее отпускание отменяет его; tap и long-hold не выполняются оба для одного экземпляра.
- При настроенном удержании выходной клавиши она зажимается при включении hold и отпускается при первом отпускании участника. Сохраняются общий учёт модификаторов, `isolate` и отложенная выдача по `holdFor`.
- Физические события поглощённых участников не восстанавливаются как обычные нажатия при завершении аккорда. Их остаточные отпускания только очищают состояние.

В первой версии использованный участник доступен для следующего аккорда после своего физического отпускания и нового нажатия. Независимые аккорды без общих участников должны работать последовательно и, где возможно, одновременно без общего глобального блокирования.

### Зачем сохранять удерживаемую выходную клавишу

Пример: `D+F` включает слой переключения окон и удерживает Alt; клавиша внутри слоя выдаёт Tab несколько раз; отпускание аккорда отпускает Alt и завершает выбор окна. Отдельные назначения `Alt+Tab` не эквивалентны непрерывному удержанию Alt.

Это дополнительная возможность поверх распознавания. Она не исправляет утечку первых букв и не заменяет буферизацию.

## 7. Пересечения с обычными правилами и условиями

Одиночное правило D допускается вместе с аккордом `D+F`: оно выполняется при возврате несостоявшегося аккорда. Его внешние эффекты не должны начинаться, пока решение об аккорде не принято.

Обычные сочетания, не пересекающиеся с новыми аккордами, сохраняют текущую обработку. Для первой версии запретить конфигурацию, где обычное многоклавишное правило и аккордовое правило с общими участниками могут одновременно действовать. Объяснить конфликт в редакторе и предложить перевести связанные правила в один режим. Не молча менять задержку и приоритет старого сочетания.

Для взаимоисключающих условий пересечение можно разрешить только если валидатор умеет доказать, что оба правила не активны одновременно. Недостаточно считать разные списки приложений автоматически непересекающимися.

Набор кандидатов фиксируется на старте сессии. Новый кандидат не включается посреди сборки из-за смены приложения, языка или game mode. При смене контекста отменить незавершённую сессию до обработки следующего нового события и вернуть ввод согласно исходному контексту; потребуется явный снимок разрешений, а не повторная проверка текущих условий во время replay. Включённый hold отпускается независимо от того, продолжают ли проходить условия его правила.

## 8. Аккорды внутри слоёв

Это отдельный этап после базового распознавания. Добавить область действия правил, не размещать многоклавишные строки в существующей таблице `HashMap<Key, ActionDef>` без отдельного разбора.

Предлагаемый приоритет для одинакового набора: правило верхнего активного слоя, затем нижние активные слои, затем глобальное правило. После выбора области применяется выбор самого длинного доступного кандидата. Все доступные расширения учитываются до фиксации короткого кандидата; детали смешения глобальных и локальных расширений покрыть отдельными тестами.

Набор активных слоёв фиксируется на старте сборки. Активация слоя завершённым аккордом влияет на последующие сессии, а не переписывает уже распознанное сочетание.

Должно быть возможно: удерживать один аккорд, включающий слой, и на свободных клавишах набирать другие аккорды этого слоя. Для удержанного триггера слоя нельзя требовать полного отпускания всей клавиатуры перед новым аккордом.

## 9. Архитектура и совместимость

Всё распознавание и конфигурация принадлежат `lhc-core`. Tauri и Slint только редактируют поля, показывают диагностику и подписываются на события core. Не реализовывать таймеры распознавания в UI.

Выделить распознаватель сессий из старого `handle_chord()` в отдельный модуль движка. Он получает физические события и выдаёт решения: ожидание, выбранный аккорд, возврат накопленного ввода. Исполнение действий остаётся в общей машине tap/hold/layer.

Состояние содержит кандидатов, участников, буфер событий, монотонные времена, дедлайн и снимок контекста. Дедлайны включаются в `next_deadline()` и `tick()`; отдельные потоки и блокирующий sleep не нужны. Проверка нового события на границе дедлайна и `tick()` должна иметь одинаковый результат. Участник ровно на границе окна считается допустимым; события позже границы сначала разрешают истёкшую сессию.

При выборе нового аккорда не отменять несвязанный hold, активный слой или макрос. Поведение самого назначенного действия, включая существующую замену активного макроса новым, сохраняется.

Остановка mapper, потеря устройства и смена конфигурации очищают буферы, экземпляры аккордов и таймеры, отпускают выданные клавиши. При остановке накопленный невыполненный текст не вводить внезапно. При смене конфигурации незавершённый ввод сначала разрешить по старой конфигурации, затем применить новую; нажатые клавиши не должны становиться новым аккордом без нового key-down.

Буферы ограничены. При переполнении завершить ожидание возвратом обычного ввода, а не терять события или выделять память без ограничения. Контроль очередности должен исключать перестановку букв относительно независимых событий.

Существующие профили не мигрируют автоматически в `chord`. Отсутствие новых правил должно сохранять прежний путь обработки и его тесты. Передача новых полей старой версии приложения не гарантирует новую семантику: импорт должен предупреждать о неподдерживаемых полях или версии формата.

Реализация mapper сейчас Linux-only. Дизайн не означает появления Windows/macOS interception; будущие backend'ы должны использовать ту же семантику core.

## 10. Интерфейс и диагностика

- Выбор типа показывать в редакторе правила; «Аккорд» требует минимум две разные клавиши.
- Показывать тип в карточке правила и подсказку: одиночные назначения участников могут ждать окно сборки.
- Окно сборки разместить в настройках поведения. Не смешивать его с порогом долгого удержания.
- При выборе слоя сохранять поле удерживаемой выходной клавиши, желательно в дополнительных настройках.
- Не показывать двойное нажатие и его таймаут для многоклавишных правил.
- Показывать конфликты смешанных режимов, дубликаты наборов после нормализации, неоднозначные кандидаты и недоступные слои.
- Порядок клавиш и алиасы не меняют идентичность набора: `Ctrl+KeyA` и `KeyA+ControlLeft` — одинаковые участники.
- Для Slint новые тексты проводить через `@tr`, `i18n::Msg`, `ui/i18n.slint` и русский PO-каталог, когда требуется Rust-сообщение. Vue использует существующие каталоги переводов.

## 11. Этапы внедрения

1. **Контракт и регрессии.** Зафиксировать текущие ordinary trigger, одиночные tap/hold/double-tap, модификаторы и lifecycle. Добавить round-trip новых полей без включения распознавания.
2. **Базовый аккордовый ввод.** Буферизация, одиночный fallback, фиксированное окно, самый длинный кандидат, отсутствие двойного нажатия, полное отпускание для повторного использования. Переключатель правила в обеих оболочках.
3. **Все существующие действия.** Интеграция слоёв, tap/hold, long-hold, удерживаемой выходной клавиши, `isolate` и `holdFor`; условия и безопасная смена конфигурации. До завершения этапа не объявлять режим полной заменой текущих правил.
4. **Область слоёв.** Аккорды внутри слоёв, приоритеты, редактор области действия и диагностика.
5. **Непрерывный набор.** Отдельно спроектировать повторное использование общей удержанной клавиши, например `D+F → F+G`. Решить, какие свежие нажатия создают следующий аккорд и как отличать повтор от удержания слоя. Включать явно; не менять базовую политику отпускания молча.

Первые четыре этапа дают раскладку из отдельных буквенных, цифровых и командных аккордов. Пятый нужен для раскладок, рассчитанных на непрерывные перекрывающиеся жесты. Стенография с накоплением уже отпущенных участников, последовательные комбинации без одновременного удержания и выбор нескольких действий из одного набора не входят в этот дизайн.

## 12. Проверки и критерии приёмки

Детерминированные тесты движка используют передаваемый `Instant`, без реальных ожиданий.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Нет новых аккордовых правил | Прежняя выдача и таймеры, без нового ожидания |
| D-down, F-down, release; `D+F → 1` | Ровно `1`, без исходных D/F |
| F-down, D-down для того же правила | Тот же результат |
| D отдельно; D имеет remap или tap/hold | Одиночное назначение сохраняется после fallback |
| D-up до F-down | Два одиночных ввода, не аккорд |
| D+F и D+F+G, G внутри окна | Только длинный аккорд |
| То же, G после окна | Короткий аккорд и отдельная G; без отмены уже выданного действия |
| Отпускание короткого полного кандидата до конца окна | Ровно короткое действие |
| Нажатие на границе окна и разный порядок `tick`/`handle` | Одинаковое документированное решение |
| Нет полного кандидата, постороннее нажатие или клик | Fallback до постороннего действия; порядок сохранён |
| Два неоднозначных максимальных кандидата | Fallback и диагностика; никакого случайного выбора |
| Независимые аккорды | Не поглощают и не отменяют друг друга |
| Аккорд удержан без hold-функции | Tap выполняется при отпускании; исходное сочетание не выдаётся |
| Аккорд → слой, короткое/долгое использование | Сохраняется выбранная tap/hold-семантика |
| Аккорд → long-hold | Один long-hold при пороге; раннее отпускание отменяет; tap не дублируется |
| Аккорд → слой + Alt; несколько Tab | Alt непрерывно удерживается до первого отпускания участника |
| `holdFor`, `isolate`, другие держатели того же модификатора | Сбалансированные press/release, без залипания |
| Все порядки отпускания участников | Нет лишних букв и залипших состояний |
| Перекрытие с использованной зажатой клавишей | Первая версия не выдаёт второй аккорд; после нового нажатия он доступен |
| Смена условий, слоёв и конфигурации в окне | Соблюдается политика снимка и отмены; нет действий нового контекста из старой сессии |
| Повторы, hotplug, stop, overflow | Ограниченный буфер, нет залпа повторов и залипания |
| Аккорд внутри слоя | Правильная область, расширения и приоритет; глобальные назначения не дублируются |
| Импорт/экспорт и повторное открытие в обеих оболочках | Поля и значения не теряются |

Добавить генеративные проверки последовательностей key-down/key-up: баланс выдачи, отсутствие повторного действия экземпляра, очистка после stop, неизменность legacy-пути. Результаты буквенной выдачи подтвердить в текстовом редакторе на Linux, а не только наличием `Out::Literal` в тесте. Для `text:` отдельно проверить используемый способ инъекции; новая логика распознавания не устраняет его платформенные ограничения.

Измерить задержку одиночных участников, обычных посторонних клавиш и выдачи аккордов при быстрых и медленных нажатиях. Проверить реальные клавиатуры с разным rollover: отсутствие физического события из-за ghosting нельзя исправить программным распознаванием.

Команды базовой проверки реализации:

```sh
pnpm install
pnpm dev
pnpm generate
cargo test --locked --workspace --features slint-shell/spell
cargo clippy --locked -p lhc-core -p slint-shell -p left-hand-control --features slint-shell/spell --all-targets --no-deps -- -D warnings
cargo run -p slint-shell --example editor -- --smoke
cargo run -p slint-shell --example interactions
pnpm tauri:dev
pnpm tauri:build
```

Графические проверки выполнять в рабочей сессии. Не запускать тяжёлые сборки параллельно при недостатке памяти. Дополнить `interactions` сценарием выбора типа, сохранения и повторного открытия аккордового правила.

Критерий завершения: пользователь задаёт тип в отдельном правиле, получает чистый результат буквенного аккорда, сохраняет одиночные назначения участников и существующие hold/layer-функции; профили без нового режима проходят прежние регрессионные проверки. Непрерывное перекрытие считается поддержанным только после отдельной приёмки пятого этапа.
