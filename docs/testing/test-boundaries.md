# Границы типов тестов

Тип теста определяется проверяемым контрактом и реальными зависимостями, а не
каталогом, названием Cargo target или наличием окна. Пирамида описывает объём
проверяемой системы; L0–L5 в [руководстве](../development/guide.md#уровни) —
отдельная классификация окружений и приёмки, а не ступени пирамиды.

## Как выбрать тип

| Тип | Граница и зависимости | Что оставляем за границей |
| --- | --- | --- |
| Модульный (unit) | Один алгоритм или компонент; входы и время контролируются тестом, внешние зависимости заменены | Реальное хранение, транспорт, desktop и устройства |
| Интеграционный | Контракт между компонентами или с адаптером ОС: реальные сериализация, файлы, IPC либо связка Slint/Rust; временные ресурсы и управляемое окружение | Полный пользовательский путь через установленное приложение и рабочий стол |
| Системный / e2e | Сквозной путь подсистемы или приложения через реальные backend; в описании обязательно указать начало и конец пути | Всё, что не входит в явно указанную цепочку; mapper e2e не подтверждает desktop |

UI-компонент с подставленным callback сохранения — компонентный тест, а не
проверка реального сохранения. Smoke описывает небольшой объём проверки,
regression — её назначение, headless — окружение; это не отдельные ступени
пирамиды. Установка пакета — системная проверка упаковки, а ручная приёмка —
способ выполнения, который может охватывать несколько типов проверок.

## Что уже есть

| Исходники | Тип и фактическая граница |
| --- | --- |
| Парсеры действий, валидация, engine с управляемыми событиями в `crates/lhc-core/src/` | Unit: правила преобразования входов в результаты без реальных evdev/uinput |
| `crates/lhc-core/src/config_document/`, `apps/slint-shell/src/document.rs`, тесты сохранения в `src/pages/*/tests.rs` | Среди тестов есть интеграционные: документ → валидация/транзакция → временные файлы или уведомления; расположение в `src` не делает их unit |
| `crates/lhc-core/tests/storage_override.rs` | Интеграционный: переменная окружения в дочернем процессе → разрешение путей → запись/чтение временного файла |
| `crates/lhc-core/tests/game_mode_lifecycle.rs` | Интеграционный: сохранённая конфигурация → документ → watcher и его перезапуск; Linux также проверяет обнаружение тестового процесса и grace period |
| `apps/slint-shell/tests/frontend.rs` | Интеграционный: Slint callbacks/таймеры → bindings → Document; тестовая software platform, без compositor и реального ввода |
| `apps/slint-shell/tests/inline_editors.rs` | Компонентный: настоящие Slint-редакторы и flush, подставленный callback сохранения; Document и файловое хранение не проверяются |
| `apps/slint-shell/src/ipc.rs`, подключённый также в `tests/ipc.rs` | Смешанный набор: разбор/проверка запросов и интеграция реальных локальных соединений, блокировок и очистки endpoint; без полного запуска приложения |
| `crates/lhc-core/tests/mapper_e2e.rs` | E2E подсистемы (L1): синтетическая клавиатура → evdev → mapper → uinput → чтение выходного устройства; без рабочего стола |
| `apps/slint-shell/examples/` | UI-сценарии: граница зависит от примера. Вызов callbacks проверяет UI-интеграцию, но не физический ввод; запуск под Weston не подтверждает KDE |
| VM-сценарии и ручная приёмка | Системные проверки и desktop e2e в объёме явно перечисленных шагов (L4/L5) |

Cargo называет отдельный target из `tests/` integration test. Это способ сборки:
здесь в таких targets есть и компонентные тесты, и mapper e2e. Аналогично
`cargo test --lib` выполняет не только unit. Число файлов или Cargo targets
не показывает пропорции пирамиды.

## Правила новых проверок

1. Выбирать наименьшую границу, которая воспроизводит ошибку: комбинации правил
   проверять в unit, согласованность документа и сохранения — в интеграции,
   работу реального backend — в системном сценарии.
2. Для интеграционного теста указать в заголовке модуля проверяемую цепочку,
   реальные и заменённые зависимости, ограничения платформы. Проверять наблюдаемый
   результат контракта: содержимое после повторной загрузки, откат после ошибки,
   доставленный запрос или обновлённое состояние.
3. Использовать временные каталоги и endpoint; process-global состояние при
   необходимости изолировать отдельным процессом. Не обращаться к пользовательскому
   конфигу и не требовать desktop или `/dev/uinput` для обычных интеграционных тестов.
4. Новые проверки публичного API размещать в `<crate>/tests/`; проверки приватных
   контрактов можно оставить рядом с кодом. Не раскрывать API и не переносить
   существующие тесты только ради классификации.
5. В e2e оставлять несколько сквозных критичных сценариев и риски реального backend.
   Не повторять там все варианты парсера, валидации и состояний редактора.

Существующие проверки сохраняем. Новые интеграционные тесты добавляем при
конкретном непокрытом контракте или регрессии; отдельная папка и дублирование
текущих сценариев ради «полноты пирамиды» не нужны. Эта классификация не является
утверждением о полном покрытии: например, получение runtime config само по себе
не доказывает выполнение действий движком.

## Запуск

Отдельные интеграционные targets без desktop:

```sh
cargo test --locked -p lhc-core --test storage_override --test game_mode_lifecycle
cargo test --locked -p slint-shell --test frontend --test ipc
```

Компонентные Slint-редакторы: `cargo test --locked -p slint-shell --test inline_editors`.
Интеграционные проверки внутри `src` входят в `cargo test --locked -p <crate> --lib`;
общего фильтра Cargo по семантическому типу теста нет. `--tests` также выбирает
targets, а не ступень пирамиды. Полные команды CI и отдельный запуск ignored
mapper e2e приведены в [общих проверках](common.md).

Чистые callback-проверки первоначального выбора layout, game-mode binding и
расчёта drag target перенесены из `examples/interactions.rs` в headless
`tests/frontend.rs`. Графический сценарий сохраняет проверки фактических
pointer/key events, геометрии, навигации и оформления. Для VM-матрицы и строгих
профилей см. [автоматическую приёмку](automation-acceptance.md#строгий-профиль-vm-приёмки).
