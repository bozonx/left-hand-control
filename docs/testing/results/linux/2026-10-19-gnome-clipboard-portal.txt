Implementation:
- GNOME Wayland libei+clipboard and Clipboard modes request Clipboard access on
  their existing RemoteDesktop session BEFORE Start and check clipboard_enabled.
- Signals subscribed before requesting access; dedicated synchronous worker keeps
  blocking destination checks/pipe I/O outside Tokio. Only signal subscription,
  polling and cleanup enter zbus's runtime.
- Preserve all offered MIME data (<=128 formats, <=64MiB aggregate); bound reads
  and writes, validate destination/cancellation before each temporary-data write.
- Restore only while still owner; a new owner wins. Restored data remains served
  after the input backend retires, until another owner replaces it.
- Permission-token caches/files separated by capability: existing keyboard file
  portal-remote-desktop.token; new portal-remote-desktop-clipboard.token for GNOME
  Clipboard sessions. No fallback from a keyboard-only grant and no re-prompt loop
  after an explicitly denied clipboard grant.
- KDE/other desktops keep their existing data-control backend; pure libei/keycode
  modes do not request clipboard access. No Shell.Eval or destination-check bypass.

Primary protocol reference:
https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Clipboard.html
GNOME restore-data includes the saved clipboard permission; capability separation
is necessary when upgrading a keyboard-only grant:
https://github.com/GNOME/xdg-desktop-portal-gnome/blob/main/src/remotedesktop.c
