# Результаты тестирования: что хранить

## Политика

Хранить в Git все выходные файлы каждого запуска не нужно. Хранить только локальные
логи тоже недостаточно: после удаления VM нельзя будет проверить, на чём основана
приёмка выпуска. Используем два уровня:

| Данные | Где хранить | Когда сохранять |
| --- | --- | --- |
| Короткий итог приёмки: среда, исходники, команды, PASS/FAIL/SKIP, ограничения | Git, `docs/testing/results/<platform>/` | Перед выпуском, при закрытии дефекта или изменении статуса платформы |
| Неуспешная значимая приёмка с открытыми дефектами | Git, краткий отчёт | Если на её основании платформа/функция не принята |
| Повторные диагностические попытки и промежуточные сводки | Локально, например `test-results/` | Пока нужны для расследования |
| Полные stdout/stderr, скриншоты, трассы ввода, профили и метрики | Локально или артефакты CI/релиза | До закрытия проблемы; важные артефакты сохранять вместе с релизом |
| VM-диски, overlay, Cargo caches, сборки и тестовые конфиги | Вне Git | По необходимости; удалять отдельно от доказательств приёмки |

Значимый FAIL не удаляем ради «зелёной истории». Следующий отчёт должен явно
указать, какой дефект исправлен и каким повторным запуском это подтверждено.
Срок хранения больших артефактов зависит от доступного места и важности выпуска;
универсальный бессрочный срок для всех диагностических попыток не задаётся.

## Текущее поведение инструментов

`e2e-local.sh` и `result_path()` VM-контроллеров пока автоматически создают короткие
`.txt` в `docs/testing/results/linux/` или `windows/`. Создание файла не означает,
что его надо коммитить. Перед `git add` выбрать значимые отчёты; промежуточные можно
перенести в игнорируемый `test-results/`. В этом изменении пути вывода runner не менялись.

Полные VM-артефакты находятся в `<vm>/runs/<timestamp>/logs`, локальный desktop-runner
выводит путь к временному каталогу. Перед очисткой `/tmp`, overlay или VM скопировать
нужные доказательства в постоянное локальное хранилище либо артефакты выпуска.
`test-results/` игнорируется Git; содержимое этого каталога само по себе не является
общедоступным свидетельством для других разработчиков.

## Существующая история

Существующие отчёты сохранены: на них уже ссылаются документы, и среди них есть
свидетельства незакрытых ограничений. Массово удалять их без разбора нельзя.
При отдельной очистке сначала:

1. Составить список ссылок и выбрать по одному значимому полному результату
   для каждой среды/версии и необходимых точечных подтверждений исправлений.
2. Сохранить локальную копию удаляемых из Git отчётов и связанных артефактов.
3. Обновить ссылки, не теряя сведения об ошибках и непройденных проверках.
4. Проверить ссылки и затем удалить только согласованный список.

Удаление файлов из HEAD не удаляет их из истории Git и почти не уменьшает размер
уже клонированного репозитория. Переписывание истории для этих небольших текстов
не требуется.

## Минимальный отчёт

```text
Дата и часовой пояс:
ОС/версия/архитектура, desktop/compositor/session:
Стенд: CI / VM / физическая машина; устройства и разрешения:
Исходники: commit; dirty/clean; SHA256 архива для dirty tree:
Пакет: версия, формат, SHA256; popup backend и способ ввода текста:
Команды (точно, включая параметры и пропуски):
Результат каждого набора: PASS / FAIL / SKIP / NOT RUN:
Открытые дефекты и причины пропусков:
Границы: что этим запуском НЕ проверено:
Артефакты: постоянный путь или ссылка; при необходимости срок хранения:
Вывод: какие требования закрыты, какие остались:
```

Не записывать секреты, IPC-токены, ключи SSH, личный конфиг или содержимое реального
буфера обмена. Абсолютный локальный путь полезен владельцу стенда, но для коллег
не заменяет доступный артефакт. Не переносить `passed` между разными пакетами,
коммитами, popup backend, ОС или приёмниками текста без отдельной проверки.

## Как читать отчёт

- `PASS` — выполненный шаг с проверенным ожидаемым результатом.
- `FAIL` — провал продукта или стенда; причину различать по журналу.
- `SKIP` — явный пропуск; не считать принятым.
- `NOT RUN` — шаг не запускался, например после раннего сбоя.
- Успех внутри гостя при обрыве контроллера описывать отдельно от полного e2e успеха.
- Зелёная сводка относится только к заявленному набору; частичный диагностический
  запуск не заменяет полный, даже если его счётчик ошибок равен нулю.
